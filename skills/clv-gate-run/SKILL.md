# CLV 构建与门禁跑批

## 触发条件

- 一批改动做完要验收；改了入库 `.cpp` / `.h`（哪怕只改注释）要补跑一轮
- 加了 / 删了用例，或退场过公开码导致探针失效
- 要出"终局态"读数写进交付记录

## 核心口径（判读顺序，不可颠倒）

1. **先看四个 `*_EXIT`**（配置、构建、双配置 ctest、各前置项）与 `GATE_DONE` / `GATE_FAIL reason=…`。
2. **再看 `… tests passed out of N` 的 N**。红构建时上一轮的二进制仍会报"300 passed"，只看这行会误判为绿。
   增量跑批脚本必须在构建失败时**跳过 ctest** 并写一条 `CTEST_SKIPPED reason=BUILD_RED`，不留假绿。
3. **ctest 例数对 `CMakeLists.txt` 里的 `CLV_EXPECTED_TESTS`**。数的是**注册数**（`out N` 那个 N），不是通过数；
   skip 与 fail 分两栏读（`***Skipped` 不等于红，也不等于没跑）。换构型（含 `CLV_COEF_CODING` 两档）不改这个数字。
4. **播放器的 `dev` 辅判据 = `|dev| ≤ period`**（30 fps ⇒ 33.3 ms）。主判据仍是 `dropped = 0`；
   `dev` 超出一整个周期才 FAIL。定得更紧就变成在读睡眠粒度（本机 1~5 ms 的唤醒量子 + 设备约 100 ms 一跳），不是在读同步。

## 环境（这台机器的实测事实）

- 必须在 **vcvars64 的同一个进程**里跑：`.bat` 内显式设 `INCLUDE` / `LIB` / `PATH`（MSVC 工具集 + Windows SDK 版本各写死一处）。
- 跑批脚本**只写 ASCII**：cmd.exe 按字节偏移重读 `.bat`，中文与控制台代码页会让后面的行错位——这条曾经吃掉一整轮基线。
  行尾是另一件事：**`.bat` 必须 CRLF**（见下面「跑批纪律」里那条同族规矩），入库文本才按 `.gitattributes` 钉的 LF；
  两份口径别混着写，本仓旧版本里写过"跑批脚本只准 LF"，那是错的。
- 生成器固定 **Ninja**（VS 生成器是多配置，缺省 win32 与 64 位第三方库打架）。
- Python 一律走 `.venv/Scripts/python.exe`；`clang-format` 不用每次指路径：`scripts/format_all.py` 按四条链找 ——
  环境变量 `CLV_CLANG_FORMAT` → 仓库根本机私有件 `.clv-tools.local`（`clang_format=` 一行，该件不入库）→ PATH →
  常见安装位置扫描（cpptools 扩展自带的 LLVM/bin、LLVM 标准安装根），并在首行打印命中的是哪一路。
  换机器时只改 `.clv-tools.local`，或干脆不写：让安装位置扫描自己找到；**别把本机绝对路径写进 `.clang-format`**，
  那份是风格件，多一个键 clang-format 直接报 `unknown key` 并拒绝格式化。
- **格式闸是三半**：C/C++（`.clang-format`）、Python（black 默认参数）、**Markdown（仓库根 `.pymarkdown`）**。
  Markdown 半吃 `pymarkdown`（pip 包名 `pymarkdownlnt`，钉在 `requirements.txt`，装法就是本仓那条
  `python -m pip install -r requirements.txt`），入口两路与 black 同形：PATH → `.venv/Scripts/pymarkdown.exe`，
  首行 `[tool] … source = …` 打的就是命中的哪一路。两路都空 = 这一半根本没跑 ⇒ 退出码 2；
  三半同则：`0` 全合格 / `1` 跑了且不合格 / `2` 有一半没跑成，`2` 绝不许读成通过。
- Markdown 半**不看工具默认退出码**：默认方案把「有违例」和「调用失败」都压成 1，分不清是没合格还是没跑成。
  `format_all.py` 因此统一带 `--return-code-scheme explicit`（实测三档：0 干净 / 4 有违例 / 1 调用失败），
  非 0 非 4 一律按「这一半没跑成」结算。覆盖面取 **git 跟踪清单里的 `.md`**——未跟踪的在制品与被 `.gitignore`
  排除的过程账都不进闸，`third-party/` 的子目录（上游文档）除外。
- 规则文件 `.pymarkdown` **只在当前工作目录查找、不沿祖先链上溯**（实测把长行探针放到子目录里跑，仓库根那份配置
  照不到，MD013 照样报），所以必须在仓库根跑。命令侧的坑：`--set <规则号>-enabled=` 这类形**实测不生效**
  （五种写法全静默无效、也不报错），开关只走配置件，临时验一条规则用 `-e/-d <规则号>`。
  还有：**规则号与 option 键写错都不报**（实测段名 `md999_bogus`、键名 `bogus_opt` 都静默通过，连 `strict-config` 也不挡），
  改规则名必须对着 `pymarkdown plugins list` 人工核。
- 有两个扩展**必须开**，缺哪个判定面就缺一块：`front-matter` 不开，`skills/*/SKILL.md` 这类 YAML 头会被当成
  setext 下划线，MD003/MD022/MD023/MD041 报出一片**假**违例（实测 84+5+5+1 处）；`markdown-tables` 不开，
  表格根本不进表解析，MD055/MD056 **一条都不报**——「单元格内手写换行把整行掉出错位」这类真缺陷就没人管
  （实测三张负控制表在关着时全默，开了才各自报出 MD055/MD056）。
- `--write`（工具的 `fix`）有两条实测限制：① 只要动一个文件就把**整件**写成 CRLF，与本仓 `.gitattributes`
  钉的 `eol=lf` 冲突，`format_all.py` 在 fix 之后自己归一回 LF 并复扫，归一不干净就按不合格报；
  ② 改动面会超出触发它的那条规则（实测对 `demo/README.md` 跑一次 `fix`：7 处示例源码制表符全被重排成空格，
  同时整件换行被改成 CRLF ⇒ 逐行差异 374 行），
  所以 `.pymarkdown` 把 MD010 整条关掉，且 `--write` 之后**必须看 `git diff` 再谈提交**。
  审美条也按实测关掉：MD013（中文长行 693 处）、MD060（紧凑竖排 922 处）、MD036（粗体行当小标题是既有层级）。

## 跑批纪律

- **跑批脚本的产物路径一律自锚在脚本自己旁边**：`set "D=%~dp0"`，之后每个重定向都写 `"%D%xxx.log"`，
  **不要靠 `cd` + 裸相对重定向**。`cd` 那行一旦没执行成（脚本被中途改过、cmd 按字节偏移重读时最容易），
  日志就落在**当时的工作目录**——常常就是仓库根。实测：根上曾残留两份零散日志（55 B 与 67 B 的零头），
  正式件 728 B / 75 B 一直在脚本自己那侧，读数值没丢。**这类事故不要用 `.gitignore` 去盖**——
  那只是把事故清单抄进配置文件，事故还在；治法是脚本自锚。
- **自锚要覆盖「不由重定向决定落点」的那一类**：工具自己命名的中间件，重定向管不到它，只看调用时的 cwd。
  实测两例落在过仓库根：① `cl` 只给 `/Fe"…\x.exe"` 不给 `/Fo` ⇒ `.obj` 落 cwd，而 `cd /d "%D%"` 写在编译行之后根本没生效；
  ② `ffmpeg … -report` 按 `ffmpeg-<YYYYMMDD>-<HHMMSS>.log` 在 cwd 落一件。
  规矩三条：**编译行一律显式 `/Fo"<锚定目录>\<名字>.obj"`**（目录路径无空格时可直接引用；写成目录名带尾反斜杠的
  `/Fo"dir\"` 会让 `\"` 被当转义引号，别用那种写法）；**`cd /d` 挪到脚本第一行动作之前**，别指望后面的 `cd` 兜住前面的编译；
  **能给 `-report` 的第三方件优先不用它**，非要留证据就先把 cwd 定到本轮日志目录再调，或在日志里登明「本件落点 = 当时的 cwd」。
  判「这条修没修好」用对照跑：同一份 TU 从同一个 scratch 目录编两次，一次带 `/Fo` 一次不带，
  看 scratch 里 `.obj` 的有无 = 1 件 vs 0 件（只跑带 `/Fo` 那一趟不构成证据）。
- **`for /f %%c in ('type x 接 find /c /v 空串')` 这类「在 for /f 里套子管道」的读数在无控制台父进程下不可信**：本轮实测两种坏法 ——
  ① 整批挂住不动（两份 bat 卡在同一个构造上，取证件白等；构建明明 `BUILD_RC=0` 已经写完）；② 计数行被打成无关串
  （`WARN_ERR_LINES=/c/Windows/zh-CN/winhlp32.exe.mui`）。要数行数就**数被重定向那个件的字节数**（0 B = 零命中）
  或把清单落件后由外部数，`for /f` 那行只当噪声读；`start "" /B <GUI 件>` 同族，父 cmd 会等 stdout 句柄关才回，跑这类件改由外部起、按时限 `taskkill`。
- **`.bat` 里 `echo` 的文案不能带 `>`**：cmd 会把它当重定向符，**只写 ASCII 是不够的**。实测一次 `echo ---- 3. CLV round trip (encode -> decode -> per-sample compare) ----`
  就在仓库根写出野件 `per-sample`（50 B），还差点被 `git add -A` 收进版本库。要写箭头就用 `=>`，或者干脆换个说法。
  顺带一条同族的：`.bat` 必须 CRLF——LF-only 会被按字节偏移错读，注释行能变成命令（本仓实测过，一轮日志里多出 `it` / `that` / `these` 三个 0 字节垃圾件）。
- **测量件的链接库必须是当前构建产物，并把库哈希留在本轮日志里**：跑测架与质量尺这类测量件常按历史路径链 `clv.lib`，
  而目标改名后那条路径会变成**旧二进制残留**（实测：一个改名前的 `build\clv.lib` 停在 10-11，之后编码路径又改过三轮，
  跑出来的数其实是旧码的数 —— 「与登记值逐字节对平零偏差」因此没有牙齿）。
  规矩三条：① 测量件一律链本轮构型产出的库，或**冻结一份仓外副本**并记其 SHA-256；② 本轮日志或清单里带上库哈希；
  ③ 判「新旧码有没有漂」的最短路径 = 同素材同档位跑两遍、比逐帧读数，别拿旧码的数当新码的基线。
- **示例直跑前要核验运行目录里的 DLL 是本轮件**：`demo_local/bin/clv.dll` 是靠 CMake 的 POST_BUILD 拷贝进去的，
  而**拷贝挂在某个 exe 目标上时，exe 不重链就不执行**——只改库内实现（导出面一字未动 ⇒ 导入库哈希不变）时 exe 不会重链，
  `bin` 里留的是上一轮的 DLL，示例读的是旧行为（实测一次：改了节器件的背压缺省，两趟读数与改前逐帧一致，核对哈希才发现
  `bin` 里是 `244968d4…` 而本轮产物已是 `785ccb35…`）。挂点已移到整份刷新目标（每次构建必执行）。
  口径：示例直跑的第一步不是跑，是 `certutil -hashfile demo_local\bin\clv.dll` 与本轮构建目录那一行对平。
- **留档清单的生成时刻必须晚于最后一个作业完成时刻**：哈希清册 / 素材清单这类件，若在并行作业还没收齐时就生成，
  会把最慢那格整个漏在窗口外，而产物随后被删 ⇒ 账面那句"全留"当场失真。实测：一份 35 条的重建件清册生成于 04:06，
  最慢那格 04:10 才跑完，四份里漏了一份；补法只能按登记配方重生（先证源件重生哈希与登记值相同，再用逐帧读数
  与留存差值两条证据证明"重生的就是产出那批图的那件"）。**边跑边落哈希 = 必漏**；要么等齐，要么落完再重生成一遍全量。
- **换 TAG 零覆盖**：每轮一个新 TAG，日志与状态件按 TAG 命名，永不复写上一轮；同一轮跑错就再开一轮，不留混合态。
- **中途禁改脚本**：跑批期间那份 `.bat` / `.py` 一个字节都不能动（同上的重读陷阱）。要改就停下这轮、改完开新 TAG。
- **对平件 rc 口径（与门禁自身的 rc 分开，别混写）**：逐格对平这类工具件的退出码固定四态，新写对平件照此设计——
  `rc=0` 全部有基准格对平且无无基准格；`rc=1` 脚本自身异常；`rc=2` 有基准格全对平但存在无基准格；
  `rc=3` 检出真偏差（有基准格不符）。**判读顺序 = 先看有没有 traceback，再看退出码**：本轮实测过一次
  SyntaxError 也返回 1，若不先看 traceback 就会把"脚本写坏了"读成"基准漂了"。
  `rc=2` 这一档是必须的：把"查无基准"并进偏差集会长期误报停手，反而把真偏差淹在噪声里
  （实测一次 24 格"无基准"被并进偏差 ⇒ 报出 rc=3、真偏差 0 格，读起来完全像基准漂）。
  门禁件自己的 `BUILD_EXIT` / `CTEST_EXIT` / `GATE_DONE` 那套是另一套语义，两处不要共用一个说法。
- 新增测试文件后记得 `tests/win32/sources.cmake` 登记，Ninja 会自动重新配置；漏登记 = 用例根本没进可执行，而 ctest 仍报旧数。
- 长任务一律走平台的后台任务（完成会唤醒会话），不要起游离进程再轮询。

## 构型开关（`CLV_COEF_CODING`）与双构型对平

- 系数编码法是**编译期构型**，不是运行时参数：`=0` 定宽 / `=1` EOB 截尾 + Exp-Golomb 幅值，默认 1。
  CMake 的 `add_compile_definitions` 打在**仓域** ⇒ 库、测试、示例必须看到同一个值（分开配 = 测试拿一种语法读另一种的产物）。
  越界值在配置期由 `FATAL_ERROR` 挡，头文件里另有 `static_assert` 兜第二层；跑批日志要带上配置值，读数离开构型没有意义。
- 换构型 = **独立 build 目录**：每个开关值一套全新目录，`cmake -S . -B <该构型目录> -DCLV_COEF_CODING=<0|1>`（目录名在配置时自定），
  两档各自一套 + 各自的冻结件目录。
  不要在原目录里改值重配：对象文件时间戳不一定重排，容易出混构型产物。
- **"改语法不该改像素"这一类，验收 = 双构型字节对平**，两把尺各钉一头：定宽侧复现**已发布基线**的字节数与素材哈希
  （对不上就是动了旧码），变长侧复现**提案沙盒**的读数（对不上就是重写引入漂移）。两侧都落纸、各带库 SHA-256；
  哈希不等时要把差异**逐字节定位到类别**（实测一次：整段差异 = 帧头选择器 1 处 + 每包 CRC 重算，块数据本体无第三类差异），
  只写"哈希不同"等于没取证。
- **整件哈希不能当"同源码复现"的尺**：MSVC 链接默认写 PE `TimeDateStamp` 并随机化 PDB GUID，同一份源码两次链出来的
  Debug `clv.dll` 必然差这几十字节（实测：3 156 480 B 里差 35 B、7 段，全在时间戳与 `.rdata` 的调试目录里，
  `.text` / `.data` / `.pdata` / `.reloc` 等逐段哈希全同）。可复现的尺只有两个：① `clv.lib`（导入库只由导出名与顺序决定，
  跨构型跨目录同值）；② 逐段哈希（代码看 `.text`）。未上 `/Brepro` 之前，拿整件哈希"复跑必须相同"当判据 = 把链接时刻读成回归。
- **判据分档只许一处 `#if`**：两档语法不同的期望值收敛在 `tests/win32/video/test_config_expect.h`，
  生成件（`scripts/gen_video_payload_fixtures.py` → `video_payload_fixtures_p.h`）**两档数组都发**（后缀 F0 / F1）、自己不选档，
  用例只引用常量。别在 `.cpp` 里补 `#if`，也别把 `block_size` 这类"选了档才知道"的数再写第二遍——
  分档头里的 `static_assert` 就是"没有第二处"的机械证明。
- **ASan 要两档各跑一把**：只跑默认档时，定宽档才走的分支（分档头 `#else` 侧常量、定宽载体的消费路径、"取错法必须被拒"那条断言）
  在 sanitizer 下等于没测。recipe：编译侧 `/fsanitize=address`（link.exe 会拒这开关 = `LNK4044`，asan 库由插桩对象推出）、
  依赖走 `build/_install_asan` 插桩专用前缀（与未插桩预编译件混链出 `LNK2038`）、`CLV_BUILD_SHARED=OFF` 让"两侧都插桩"按构造成立、
  CRT 保持 `/MDd` —— **在 `build.ninja` 里核时要找 `-MDd`，找 `/MDd` 会得到假零**（CMake 给 Ninja 写的是短横形式）。
  ctest 只回显失败用例的 stderr ⇒ 抓报错必须再单进程跑一遍全量测试：直接运行该构型目录下的 `clv_tests` 可执行件、
  stdout 与 stderr 一起重定向进同一份日志，再对这份日志按列普查——ASan 报错行按 `ERROR: AddressSanitizer: <类型>`
  的类型分组计数；泄漏一栏单独数行（含 `leaked in` / `byte(s) leaked` / `LeakSanitizer` / `detect_leaks` /
  `Direct leak` / `Indirect leak` 任一即进栏）；另附 `SUMMARY: AddressSanitizer` 行与 `tests passed`、
  `[  PASSED  ]`、`***Failed`、`Total Test time` 汇总行。日志编码混着 ASCII 与 OEM 中文，统一按替换模式读
  （如 Python `errors="replace"`）。MSVC ASan 无 LSan ⇒ 泄漏一栏 0 只写"工具链不适用"，不等于已验证零泄漏。
- **两档共同的判据留在公开 ABI 面**：「取错法必须被拒」这类只断到"这一帧被拒、且拒在帧头之后"，不定位到实现行——
  伸手拿实现层符号会把"只吃公开头"这条边界拆掉；要行级定位另开白盒测试单。
- 三件哈希配成一对读：`clv.lib`（导入库）不变 = **函数面**一字未动；`clv.dll` 变而 `clv.lib` 不变 = 只改了实现或值域。
  注意枚举值**不进符号表**，尾部追加一个错误码不会改导入库哈希 ⇒ 值域变更要靠下面的镜像表复扫，不能拿这条哈希当证据。
- 两把库的读数**不进同一张表**：留档的旧库数据在表头标库哈希前缀，新跑的标当前库前缀。

## 例数变了要同步的地方（一处不漏）

1. 门禁脚本里的期望例数 `EXPECT`（**改前改后都要记**，回执里写 `300 → 316` 这种形态）。
   `EXPECT` 的值**不由执行体自裁**：执行体只数出本轮 N，取证用门脚本的副本（只改 `EXPECT` 一行），不改仓内正式闸的数字。
   实测一轮：加了一整个测试 TU 后仓内闸仍 `EXPECT=322`、本轮数出 `335`，两处差异写进回执等拍定——
   就地覆盖会把"例数没被拍过"这件事抹掉。
2. `ARCHITECTURE.md` 的「共 N 例」与分域表、`tests/docs/README.md` 的合计与分域行、`API.md` 验收清单里的例数、
   **`README.md` 的 `ctest` 行**（这张表最容易漏——它只写 `N/N`，不带上下文）。
3. **改了哪个域，那个域的测试项文档也要改**：`tests/docs/<域>.md` 的「现状」例行数，以及「判据」行里新格点的描述——
   只改合计不改分项，读者按分项相加对不上合计。
4. `CHANGE.log` 的**测试情况**条目：`旧 → 新` 带算式（哪几例、并进哪个 TU、域计数怎么变），漏记等于对外声称断档。
5. 分域计数自己算一遍再写：`for d in core api container audio video independent; do cat tests/win32/$d/*.cpp | grep -c '^TEST('; done`，
   相加必须等于 ctest 报的 N——不相等说明有用例没登记进 CMake 或有文件被算重。
6. 改完**拿旧数复扫全仓**：`grep -rn "316" README.md API.md ARCHITECTURE.md tests/docs/ CHANGE.log` 应只剩 `CHANGE.log` 里的历史条目。
   闸自己绿不代表声称跟上了——`EXPECT` 改了就改、对外文本还写旧数，这一类"改了判据没改声称"要扫过才算收。

## 公开码拆分 / 退场时的同步点（一处不漏）

一个码的**语义收窄**与**新码追加**是两类改动，但同步面是一样的六处，漏哪处都不会让门禁变红：

1. `include/<域>.h` —— 枚举行注释 + 受影响入口的 doc 行（doc 行指错码是本轮实测到的第一种漏）。
2. `src/<域>/status.h` —— 实现层同名枚举。
3. `StrError` 的分支。
4. 各个产出该码的出口（收窄后要逐出口复核判据落在哪一侧：声明侧建不成句柄 vs 逐调用侧只拒一次）。
5. 测试里的**手抄镜像表** —— `tests/win32/video/test_video_headers.cpp` 逐值那条（`64..84` 全覆盖 + `73/78/81/82` 故意留白），
   它是"值域全覆盖"这个声称的唯一载体，漏一行 = 声称断档而不是失败。
6. 程序化判据的下游 —— `scripts/cross_model.py` 按码分类的几处（改码而跨模型对照脚本还判旧码，会把"拒了"读成"拒错档"）。

值域有洞要说清并留着不复用；追加一格不会改导入库哈希（枚举不进符号表），别拿那条哈希当"值域没动"的证据。

## 门禁盖不到的一类

配置 A 是 demos ON，但它**只编译示例、不跑示例**。示例是"天然的外部 ABI 消费者"，
公开头改了版本号 / 枚举后，示例里钉死的期望值会悄悄失效——必须由本规程补一步手工直跑：

```bash
cmake --build build                      # 或门禁的净构建目录
cd demo_local && ./bin/clv_demo_core.exe; echo "rc=$?"
           && ./bin/clv_demo_container.exe; echo "rc=$?"
```

两份示例都要 `rc = 0`，且自动判定项全过（人工判定项单独在回执里标出来）。

## 内存安全构型（别把三格混成一格）

- **内存安全 = 真结果**：ASan 构型下全量用例通过、ASan 零命中；有效性用故意造的 UAF 探针自证（能看到
  `ERROR: AddressSanitizer: heap-use-after-free` 才算探针成立）。
- **泄漏 = 本工具链不可达**：MSVC 的 ASan 报 `detect_leaks is not supported on this platform`。
  这一格只能写"零命中"，**不等于已验证零泄漏**；要真数得另走 CRT leak debug 或定点探针。
- **UB = 不支持且有假绿陷阱**：`cl` 对 `/fsanitize=undefined` 只报 `warning D9002 忽略未知选项`**且退出码 0**
  ——以退出码判"过了"就是假绿，必须去日志里确认该选项真的生效过。
- ASan 构型要把第三方一起重编进独立前缀：主构型的未插桩预编译件与插桩对象混链会报
  `LNK2038: annotate_string / annotate_vector / annotate_optional`。

输出：按判读顺序给结论（先 `GATE_DONE` / 各 `*_EXIT`，再 `100% tests passed out of N`）+ 双配置各自的

## 注意事项

- "构建绿但 ctest 跳过"是**有效结论**，不是失败：把它写成 `CTEST_SKIPPED reason=…`，别默默少跑。
- 一次改动跨多个文件时，编译期错误常来自**没编译到的目标**（示例 / 探针）——链接失败也算门禁的一部分，别只看测试数。
- 门禁的判据一栏（冻结值）复跑后要逐值比对，不是"跑绿就行"：冻结值漂了说明改了不该改的行为。
- 红一轮不算坏事，红完必须留痕：状态件、失败清单、归因、以及"改前 / 改后"两轮读数一起写进回执。
